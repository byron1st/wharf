# Task 에 Todo 추가 — POST/GET /todos, PUT/DELETE /todos/{id}

Report: [20261026145819_DEV-18_IMPL_task-todo.md](./20261026145819_DEV-18_IMPL_task-todo.md)

출처: Notion 개발 이슈 보드 DEV-18 "Task 에 Todo 추가". 브랜치 `feat/dev-18-task-todo` (base `40c03a74c`). 사용자 지시에 따라 계획은 Claude 가 자체 승인했고, 사용자 판단이 필요한 결정은 아래 Key decisions 에서 Claude 가 정했다(PR 본문에 같은 목록을 남긴다).

이슈 요구사항 요약:

- Task 와 구분되는 Todo 개념. Todo 는 Task 하나에 귀속되고(하나의 Todo 는 하나의 Task 만), Task 하나가 여러 Todo 를 갖는다. 모든 origin 의 Task 가 Todo 를 가질 수 있다.
- Todo 필드: description, isDone, start date(선택), end date(선택), reminders(`[]Date`, 선택). Todo 끼리는 계층이 없다(flat list).
- DB 에는 Task 와 별도로 저장하고, Task ↔ Todo 연결 테이블을 따로 두며 이 테이블에 Task 안의 Todo 순서를 저장한다.
- API: `POST /todos`, `GET /todos`(`task_id`, `today`, `end_date`, `is_done` 조합 필터), `PUT /todos/{id}`, `DELETE /todos/{id}`.

## Non-goals

- `GET /todos/{id}` 단건 조회, `GET /tasks/{id}` 응답에 todos 포함. todo 조회는 `GET /todos?task_id=` 로 한다.
- reminder 알림 발송·스케줄링. reminders 는 저장·조회만 한다.
- 순서만 바꾸는 별도 reorder API, 부분 수정(PATCH). 순서 변경은 PUT 의 `position` 으로 한다.
- 페이지네이션, 정렬 옵션, `task_id`·`today`·`end_date`·`is_done` 외의 필터.
- Jira 쪽에 todo 를 되돌려 쓰기. todo 는 wharf 에만 있다.
- 새 마이그레이션 파일. 배포 전 예외에 따라 `0001_initial_migration.sql` 을 직접 고친다(AGENTS.md). 기존 로컬 `wharf.db` 재생성은 수동.
- 기존 task API 의 요청·응답 형태, 기존 sentinel 이름 변경. `tests/e2e` 신설, 인증·권한.

## Key decisions

- **계층 배치** — DEV-16 과 같다. route(`internal/server`) 는 요청 디코딩·쿼리 파싱·응답 매핑·상태 코드, 입력 검증과 규칙은 `internal/service`, 저장·조회는 `db.Manager` 의 새 메서드. 도메인 타입은 `internal/pkg/todo` 패키지의 `todo.Todo` 로 새로 둔다(`task.Task` 는 바꾸지 않는다). service 가 db 의 not-found 를 자기 sentinel 로 바꿔 server 가 adapter 를 import 하지 않게 한다. 기존 `Service`·`db.Manager` 인터페이스에 메서드를 추가한다(새 인터페이스를 만들지 않는다).
- **스키마** (0001 에 추가)
  - `todos (id INTEGER PRIMARY KEY AUTOINCREMENT, description TEXT NOT NULL, is_done BOOLEAN NOT NULL DEFAULT 0, start_date TEXT, end_date TEXT)`. 날짜는 `YYYY-MM-DD` 문자열(NULL 가능)로 저장해 사전순 비교가 곧 날짜 비교가 되게 한다.
  - `task_todos (todo_id INTEGER PRIMARY KEY NOT NULL, task_id TEXT NOT NULL, position INTEGER NOT NULL)` — 이슈의 "Task ↔ Todo 연결 테이블". `todo_id` 가 PK 라 todo 의 task 는 하나다. `(task_id, position)` 조회 인덱스를 둔다. position 은 task 안에서 0 부터 빈틈 없는 정수다.
  - `todo_reminders (todo_id INTEGER NOT NULL, remind_at DATETIME NOT NULL, PRIMARY KEY (todo_id, remind_at))` — DEV-17 처럼 목록 값을 JSON 컬럼이 아닌 테이블로 둔다.
  - FK 는 두지 않는다(기존 스키마 관례, `PRAGMA foreign_keys` 미사용). 정합성은 db.Manager 쓰기 메서드가 트랜잭션 안에서 지킨다.
- **Todo ID** — 정수(`INTEGER PRIMARY KEY AUTOINCREMENT`, JSON number). todo 는 항상 wharf 에서만 생기므로 task 의 `{originated}-{key}` 형식·카운터가 필요 없다. AUTOINCREMENT 로 삭제된 ID 를 재사용하지 않는다. 경로의 `{id}` 가 정수가 아니면 404(그런 todo 는 없다).
- **날짜 표현** — `start_date`·`end_date` 는 달력 날짜다. API 는 `"YYYY-MM-DD"` 문자열 또는 null, 형식이 틀리면 400. `start_date > end_date` 면 400. `reminders` 는 시각이 필요하므로 RFC3339 문자열 배열이다. 저장 시 중복을 하나로 합치고 응답은 시각 오름차순이며 항상 배열(빈 배열 포함)이다. reminder 가 start/end 범위 안인지는 검사하지 않는다. 도메인 타입에서 날짜를 어떻게 들고 다닐지(문자열, `time.Time` 등)는 구현 재량이나, 시간대 때문에 날짜가 하루 밀리지 않아야 한다.
- **Task 존재 검증** — `POST`·`PUT` 의 `task_id` 는 저장된 task 여야 한다(origin 무관). 없으면 400(`service` sentinel, 요청 본문이 가리키는 대상이 없음). task 관계와 달리 todo 는 task 에 귀속되므로 dangling 을 허용하지 않는다. 검사와 쓰기는 같은 트랜잭션에서 한다.
- **SQLite 쓰기 우선 트랜잭션 규칙 유지** — 쓰는 트랜잭션은 쓰기 문장으로 시작하고(`busyTimeoutPragma` 주석), 존재 확인은 읽기 선행 대신 쓰기의 영향 행 수(`:execrows`, `INSERT ... SELECT ... WHERE EXISTS` 등)로 판별한다. 쿼리 형태는 구현 재량.
- **요청 본문** (POST/PUT 공통) — JSON `{task_id, description, is_done, start_date, end_date, reminders, position}`. 모르는 필드(`id` 포함)·잘못된 JSON·후행 데이터는 400, 너무 큰 본문은 413(task 디코딩과 같은 규칙). `task_id` 가 공백뿐이거나 `description` 이 공백뿐이면 400. `is_done` 생략은 false.
- **순서(position)** — POST 는 그 task 목록의 끝에 붙인다(`position` 을 보내면 그 위치에 끼워 넣는다). PUT 은 전체 교체지만 `position` 만 선택이다: 생략(null)이면 같은 task 안에서는 현재 위치를 유지하고, task 가 바뀌면 새 task 의 끝에 붙인다. 보내면 그 index 로 옮긴다. 음수는 400, 목록 길이 이상이면 끝으로 간다. 옮기거나 지우면 원래 task 와 새 task 모두 0..n-1 로 다시 번호가 매겨진다.
- **PUT `/todos/{id}`** — `task_id`, `description`, `is_done`, `start_date`, `end_date`, `reminders`(전체 교체)를 요청 본문으로 바꾸고 204. `task_id` 를 바꾸면 todo 가 다른 task 로 옮겨진다. 없는 todo 는 404.
- **DELETE `/todos/{id}`** — todo 행, 연결 행, reminder 행을 지우고 같은 task 의 나머지 position 을 당긴 뒤 204. 없으면 404.
- **Task 삭제 시 todo 도 삭제** — todo 는 task 에 귀속되므로 기존 `db.Manager.DeleteTask` 가 같은 트랜잭션에서 그 task 의 todo·연결·reminder 행을 함께 지운다. Jira 동기화(`UpsertTasks`)는 task 를 지우지 않으므로 Jira task 의 todo 는 동기화 후에도 남는다.
- **GET `/todos` 필터** — 쿼리 파라미터는 AND 로 조합하고, 없으면 그 조건을 걸지 않는다(파라미터가 하나도 없으면 전부).
  - `task_id=` : 그 task 의 todo 만(없는 task 면 빈 목록, 404 아님).
  - `today=YYYY-MM-DD` : `start_date <= today` 이거나 `start_date` 가 없는 todo. 이슈 정의 그대로이며 `is_done`·`end_date` 는 보지 않는다.
  - `end_date=YYYY-MM-DD` : `end_date` 가 같은 todo.
  - `is_done=` : `strconv.ParseBool` 로 해석한다(`true`/`false`/`1`/`0` 등).
  - 날짜·bool 형식이 틀리면 400. 모르는 파라미터는 무시한다. 응답 순서는 `task_id`, `position` 오름차순(같은 task 안에서는 저장된 순서).
- **응답 형태** — todo 객체는 `{id, task_id, description, is_done, start_date, end_date, reminders, position}`(날짜 없으면 null, reminders 는 항상 배열).
  - `GET /todos` → 200 `{"todos":[todo...]}`(없으면 `[]`).
  - `POST /todos` → 201 `{"id":N}`. 단건 GET 라우트가 없으므로 `Location` 헤더는 넣지 않는다.
  - `PUT`·`DELETE` → 204.
- **에러 → 상태 코드** — 기존 `errorStatuses` 표에 todo sentinel 을 추가한다: 디코딩·쿼리·입력 검증 실패와 없는 task 는 400, 큰 본문 413, 없는 todo 404, 그 외 500. 4xx 본문은 기존과 같은 `{"error":"..."}`.

## Acceptance Contract

| ID | Observable condition | Evidence |
| --- | --- | --- |
| AC-1 | 0001 적용 후 `todos`, `task_todos`(todo_id PK, `(task_id, position)` 인덱스), `todo_reminders` 테이블이 있고 `tasks` 테이블에는 todo 컬럼이 없다. | db 스키마 테스트 |
| AC-2 | `POST /todos` 가 저장된 task(local·jira 모두)에 todo 를 만들고 201 `{"id":N}` 을 반환한다. position 생략 시 그 task 목록의 끝, 지정 시 그 위치에 들어가고 뒤 항목이 밀린다. reminders 는 중복 없이 저장된다. 없는 task, 공백 description/task_id, 잘못된 날짜·`start_date > end_date`, 음수 position, 잘못된 JSON·모르는 필드는 400 이고 아무것도 저장되지 않는다. | db 테스트(직접 SQL 로 행·position 확인), service 테스트, server 테스트 |
| AC-3 | `GET /todos` 가 `task_id`·`today`·`end_date`·`is_done` 을 AND 로 조합해 거른 todo 를 `task_id, position` 순으로 반환한다. `today` 는 start_date 가 없거나 today 이하인 것만, `end_date` 는 같은 날짜만 고른다. 각 항목은 reminders 를 시각 순 배열로 담는다. 형식이 틀린 날짜·bool 은 400. | db 필터 조합 테스트, server 쿼리 파싱 테스트 |
| AC-4 | `PUT /todos/{id}` 가 모든 필드와 reminders 를 교체하고 204 를 반환한다. position 생략 시 같은 task 안에서는 위치 유지, task 를 바꾸면 새 task 의 끝으로 가고 원래 task 의 position 이 0..n-1 로 당겨진다. position 지정 시 그 위치로 옮긴다(길이 이상이면 끝). 없는 todo 는 404, 검증 실패·없는 task 는 400 이며 이때 아무것도 바뀌지 않는다. | db 이동·재정렬 테스트, service 테스트, server 테스트 |
| AC-5 | `DELETE /todos/{id}` 가 204 를 반환하고 todo·연결·reminder 행이 사라지며 같은 task 의 나머지 position 이 0..n-1 로 당겨진다. 없는 id(정수가 아닌 id 포함)는 404. | db 삭제 테스트, server 테스트 |
| AC-6 | `DELETE /tasks/{id}` 가 그 task 의 todo·연결·reminder 행도 지우고 다른 task 의 todo 는 남긴다. Jira task 를 `UpsertTasks` 로 다시 저장해도 그 todo 는 남는다. | db 테스트 |
| AC-7 | 기존 task API·`/healthz`·`POST /tasks/jira` 동작과 기존 테스트가 그대로 통과한다. `MockService`·`MockManager` 가 새 메서드로 재생성되어 있고 `make gen` 후 diff 가 없다. | 기존 테스트, `make gen` |

검증하지 않는 위험: 동시 요청 간 position 경합(단일 연결 + busy_timeout 에 맡김), reminder 와 start/end 범위의 일관성, 기존 로컬 `wharf.db` 재생성(수동), 매우 많은 todo 에서의 재번호 비용.
