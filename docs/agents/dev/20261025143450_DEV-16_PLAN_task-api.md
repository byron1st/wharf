# Task 관련 API 추가 — GET/POST /tasks, GET/PUT/DELETE /tasks/{id}

Report: [20261025143450_DEV-16_IMPL_task-api.md](./20261025143450_DEV-16_IMPL_task-api.md)

출처: Notion 개발 이슈 보드 DEV-16 "Task 관련 API 들 추가" 와 그 안의 "DEV-17 에서 넘어온 항목". 사용자 지시에 따라 계획은 Claude 가 자체 승인했고, 사용자 판단이 필요한 결정은 아래 Key decisions 에서 Claude 가 정했다(PR 본문에 같은 목록을 남긴다).

## Non-goals

- 목록 API 의 페이지네이션·필터·정렬 옵션, 검색.
- 관계의 순환(A→B→A, 더 깊은 cycle) 검증, `parent_id` 가 `children_ids` 에도 들어 있는 모순 검증. 자기 참조만 막는다.
- 관계가 가리키는 task 의 존재 여부 검증. DB 설계상 관계는 저장되지 않은 task 를 가리킬 수 있다(DEV-17 결정).
- Jira task 를 PUT 으로 수정하기, Jira 쪽에 변경을 되돌려 쓰기.
- local key 접두어 `WHF` 의 TOML 설정화(아래 결정 참고).
- 새 마이그레이션 파일. 배포 전 예외에 따라 `0001_initial_migration.sql` 을 직접 고친다(AGENTS.md).
- `tests/e2e` 신설, 인증·권한, `writeInternalError` 의 500 응답 형태 변경(현재 테스트가 원인 문자열을 응답에 싣는 동작을 고정하고 있다).

## Key decisions

- **계층 배치** — route(`internal/server`) 는 요청 디코딩·응답 매핑·상태 코드만, 입력 검증과 규칙(자기 참조, local 전용 수정, 상태 기본값)은 `internal/service`, 저장·조회는 `db.Manager` 의 새 메서드. server 는 adapter 를 import 하지 않으므로, service 가 db 의 not-found 를 자기 sentinel 로 바꿔 돌려준다.
- **상태 코드 매핑 표 신설** (DEV-17 이월 1) — server 에 service 에러 → 상태 코드 매핑을 한 곳에 둔다: 입력 검증 실패 400, task 없음 404, local 이 아닌 task 수정 409, 그 외 500(기존 `writeInternalError` 그대로). 4xx 응답 본문은 `{"error":"<메시지>"}` 다. 잘못된 JSON·모르는 필드·너무 큰 본문도 400.
- **자기 참조 검증** (DEV-17 이월 1, 합의 사항) — PUT 에서 `parent_id == id`, `children_ids`·`linked_ids` 에 자기 ID 가 있으면 service sentinel(예: `service: task cannot reference itself`)로 400. POST 는 ID 가 저장 시점에 정해지므로 검사 대상이 없다(다음 번호를 추측해 넣는 경우는 수락된 위험).
- **local key 접두어** (DEV-17 이월 2, Claude 결정) — TOML 로 옮기지 않고 상수 `WHF` 를 유지하며 `internal/pkg/task/id.go` 의 TODO 주석만 지운다. 이유: 접두어를 바꾸면 기존 task 와 접두어가 섞이고 카운터는 하나라서 얻는 것이 없으며, 요구도 없다.
- **cross-origin parent-children 허용** (DEV-17 이월 3, Claude 결정) — local task 가 Jira task 를 child 로 선언하는 것을 허용한다(개인 task 아래에 Jira 티켓을 묶는 용도). 대신 소유 규칙을 하나 바꾼다: **local 이 아닌 task 를 저장할 때 그 task 가 parent 를 선언하지 않으면, local task 를 parent 로 하는 행은 지우지 않는다.** 같은 origin 의 parent 행은 지금처럼 지운다. Jira task 가 parent 를 선언하면 지금처럼 그 parent 로 교체된다(parent 는 하나, Jira 가 이긴다). local task 를 저장할 때는 지금처럼 parent 행을 전부 소유한다.
  - 거절한 대안: POST/PUT 의 `children_ids` 를 local ID 로 제한 — 단순하지만 Jira 티켓을 local task 아래에 묶을 수 없다. links 는 이미 선언자 소유라 충돌이 없다.
- **children 의미** — Jira 동기화(`UpsertTasks`)의 children 은 지금처럼 추가·재지정만 한다. local task 의 POST/PUT 은 전체 교체다: PUT 은 `parent_id = 자기` 행을 모두 지우고 선언한 children 으로 다시 넣는다. POST 는 새 ID 라 기존 행이 없다.
- **PUT 은 local task 만** (Claude 결정) — Jira task 는 다음 동기화에 덮어써지므로 PUT 하면 409. `id`·`originated` 는 바꿀 수 없고 그 외 필드(title, description, status, start_date, due_date, parent_id, children_ids, linked_ids)는 요청 본문으로 전부 교체한다(빠진 필드는 빈 값). DELETE 는 origin 과 관계없이 허용한다(Jira task 는 다음 동기화에 다시 생긴다).
- **요청 본문** (POST/PUT 공통) — JSON `{title, description, status, start_date, due_date, parent_id, children_ids, linked_ids}`. 모르는 필드는 거부한다(`id`·`originated` 를 보내면 400). `title` 은 공백만이면 400. `status` 는 비어 있으면 `todo`, `task.Status` 의 네 값이 아니면 400. 날짜는 RFC3339 또는 null.
- **응답 형태**
  - summary(목록 수준): `id, originated, title, description, status, start_date, due_date`. 관계 필드는 없다. 날짜가 없으면 null.
  - `GET /tasks` → 200 `{"tasks":[summary...]}`, `id` 오름차순. description 은 100 rune 을 넘으면 앞 100 rune + `…` 로 자른다(UTF-8 안전, 100 rune 이하는 그대로). 자르기는 응답 표현이므로 server 에서 한다.
  - `GET /tasks/{id}` → 200 summary 필드(description 전체) + `parent_id`(없으면 null), `children_ids`, `linked_ids`(항상 배열) + `parent`(summary 또는 null), `children`, `linked`(summary 배열, 잘린 description). ID 목록은 DB 의 관계 행 그대로(저장되지 않은 task 포함)이고, summary 는 저장된 task 만 담는다. children 은 `task_hierarchies.parent_id = id` 행, linked 는 `task_links` 의 `task_id = id` 와 `linked_id = id` 합집합(중복 제거). 없으면 404.
  - `POST /tasks` → 201, `Location: /tasks/{id}`, `{"id":"local-WHF-NNN"}`. 생성은 기존 `db.Manager.CreateLocalTask` 를 쓴다.
  - `PUT /tasks/{id}`, `DELETE /tasks/{id}` → 204.
- **DELETE** — 한 트랜잭션에서 `tasks` 행과 `task_hierarchies` 의 `child_id = id`·`parent_id = id` 행, `task_links` 의 `task_id = id`·`linked_id = id` 행을 지운다. 다른 task 는 건드리지 않는다(cascade 없음). 없으면 404.
- **SQLite 쓰기 트랜잭션 규칙 유지** — 쓰는 트랜잭션은 쓰기 문장으로 시작한다(`busyTimeoutPragma` 주석). 존재 확인이 필요하면 읽기 선행 대신 쓰기의 영향 행 수로 판별한다. 순수 읽기는 트랜잭션이 필요 없다.
- **조회 인덱스** — 읽기 쿼리를 추가하므로 DEV-17 합의대로 `task_hierarchies(parent_id)`, `task_links(linked_id)` 인덱스를 0001 에 추가한다. 기존 로컬 `wharf.db` 는 지우고 다시 만들어야 한다.
- **기존 라우트 영향** — `GET /tasks/{id}` 가 `GET /tasks/jira` 와 매칭되므로 그 요청은 이제 405 가 아니라 404(task 없음)다. `POST /tasks/jira` 는 더 구체적인 패턴이라 그대로다. 405 를 확인하는 기존 테스트는 가려지지 않는 경로로 바꾼다.

## Acceptance Contract

| ID | Observable condition | Evidence |
| --- | --- | --- |
| AC-1 | `GET /tasks` 가 저장된 모든 task 를 `{"tasks":[...]}` 로 id 오름차순 반환하고, 각 항목은 summary 필드만 가지며 100 rune 초과 description 은 앞 100 rune + `…`, 이하는 그대로다(멀티바이트 문자에서 깨지지 않음). 빈 DB 는 `{"tasks":[]}`. | server 테스트(MockService), db 목록 조회 테스트 |
| AC-2 | `GET /tasks/{id}` 가 전체 description 과 `parent_id`/`children_ids`/`linked_ids`, 그리고 저장된 관계 task 의 summary(`parent`/`children`/`linked`)를 반환한다. linked 는 양방향 합집합이고, 저장되지 않은 관계 ID 는 ID 목록에만 있다. 없는 id 는 404. | db 조회 테스트(양방향 링크·dangling 관계), service 테스트, server 테스트 |
| AC-3 | `POST /tasks` 가 201·`Location`·`{"id":"local-WHF-NNN"}` 을 반환하고 task 는 `originated=local` 로 관계와 함께 저장된다. status 생략 시 `todo`. 빈 title, 알 수 없는 status, 잘못된 JSON, 모르는 필드(`id` 포함)는 400 이고 저장되지 않는다. | service 테스트, server 테스트 |
| AC-4 | `PUT /tasks/{id}` 가 local task 의 id·originated 외 모든 필드와 parent·children(전체 교체)·links 를 바꾸고 204 를 반환한다. 자기 참조(parent/children/linked)·검증 실패는 400, 없는 id 는 404, local 이 아닌 task 는 409 이며 이때 아무것도 바뀌지 않는다. | db 수정 테스트(children 교체 포함), service 테스트, server 테스트 |
| AC-5 | `DELETE /tasks/{id}` 가 204 를 반환하고 그 task 행과 그 task 가 child·parent·선언자·대상인 관계 행이 모두 사라지며 다른 task 행은 남는다. 없는 id 는 404. | db 삭제 테스트, server 테스트 |
| AC-6 | local task L 이 Jira task J 를 child 로 저장한 뒤, parent 가 없는 J 를 `UpsertTasks` 로 다시 저장해도 `(J, L)` 행이 남는다. J 가 Jira parent P 를 선언하면 `(J, P)` 로 교체된다. Jira parent 를 갖던 Jira task 가 parent 없이 저장되면 그 행은 지금처럼 지워진다. | db 테스트 |
| AC-7 | 0001 적용 후 `task_hierarchies(parent_id)`, `task_links(linked_id)` 인덱스가 있다. `id.go` 의 TODO 주석이 없고 local key 는 여전히 `WHF-NNN` 이다. | db 스키마 테스트, 코드 |
| AC-8 | `GET /healthz`, `POST /tasks/jira` 동작이 그대로이고, 405 확인 테스트는 가려지지 않는 경로로 통과한다. mock(`MockService`, `MockManager`)이 새 메서드로 재생성되어 있다. | 기존 server 테스트, `make gen` 후 diff 없음 |

검증하지 않는 위험: POST 에서 다음 local 번호를 추측해 자기 참조를 넣는 경우, 관계 cycle, 동시 요청 간 경합(단일 연결 + busy_timeout 에 맡김), 기존 로컬 `wharf.db` 재생성(수동).

## Authority Boundaries

- Discretion: db·service·server 의 메서드·타입·sentinel·헬퍼 이름과 시그니처, 쿼리 구성(목록·ID 묶음 조회·관계 조회의 쿼리 개수와 형태, `sqlc.slice` 사용 여부), 요청 본문 크기 제한 값, 4xx 로그 레벨, 테스트 구성. service sentinel 의 "return site 하나" 관례를 지키기 위한 분리·헬퍼 방식.
- Must-ask: Key decisions·Non-goals 변경(상태 코드, 응답 형태, cross-origin 규칙, PUT local 전용, children 의미), 새 마이그레이션 파일, `task.Task` 필드 변경, 서드파티 의존성 추가. (이번 실행에서는 사용자 지시에 따라 Claude 가 결정하고 PR 에 기록한다.)
- Stop conditions: sqlc 가 필요한 조회를 생성하지 못해 손으로 쓴 SQL 이 필요할 때(생성 코드 경계 위반 여부를 판단해야 함), cross-origin 규칙 변경이 DEV-17 의 기존 소유 규칙 테스트와 정면으로 충돌할 때.
- Loop budget: 3
